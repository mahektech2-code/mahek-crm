On the handset a lead is a row in SQLite `leads` (keyed on the same id as the office's `customers` row), samples are rows in `samples`, and every change goes up as an outbox item: `entityType: "lead"`, `"sample"`, `"lead_validation"`, `"lead_communication"`. The rules are **not reimplemented** — `mbos-app/src/engines/funnel/` is a byte-for-byte copy of the office's funnel files, pinned by a test. The server re-checks everything in `handleLead`, `handleSample` and `handleLeadValidation`.

## Changing it safely

<Steps>
<Step title="Change a gate or a ladder on the SERVER copy">
Edit `src/lib/engines/lead-gates.ts` (or the ladder, labels, role-action), then copy it over the handset file. Never edit `mbos-app/src/engines/funnel/` directly — the mirror test fails. Watch the one import line that differs (`cp` breaks it; CI catches it).
</Step>
<Step title="Add a lead field">
Add the column to the handset's `leads` table, the office's `customers`, `leadSchema`/the update schema, and `upsertLeads`. A field the hand-rolled pull reads but the server does not send is written as NULL over the local value.
</Step>
<Step title="Ship a new APK">
The funnel copy ships in the bundle; a gate change does not reach phones until they update. The server still enforces the new rule meanwhile.
</Step>
</Steps>
