The book is decided on the server (`customerIdsInScope`), shaped once per channel (`customersForDevice`, reused by bootstrap and delta), stored in the handset's `customers` table, and read through two SQL builders in `mbos-app/src/data/customer-query.ts`. Every word on a card comes from a pure file — `lib/account-label.ts`, `engines/leads.ts` `reorderState`, `engines/statement.ts` — because `data/customers.ts` imports SQLite and cannot be tested off a device, which is exactly how a branch that could never fire shipped on the most-read screen in the app.

## The handset's book

<Code file="mbos-app/src/data/customer-query.ts" symbol="IS_LEAD" />

<Code file="mbos-app/src/data/customer-query.ts" symbol="LEAD_FACTS" />

A lead is a row in **both** handset tables: the office sends leads on their own channel into `leads`, keyed on the same id as the `customers` row. So "is this a lead" is an `EXISTS`, never a column read, and `archived = 0` is part of it — an archived lead leaving the Customers half too would put the shop on no screen at all. The facts are correlated subqueries rather than a join, because both tables carry `id`, `name` and `city`. On the Customers half the three facts are constants (`NOT_A_LEAD`), saving thirty thousand point lookups on a large book.

## Changing it safely

<Steps>
<Step title="Add a customer column to both sides at once">
A server column the handset should show goes into `customersForDevice` **and** a handset migration in the same release pair — server first, but never a column the old build cannot hold.
</Step>
<Step title="Keep words in the pure files">
Any new label on a card goes into `account-label.ts` (or an engine) with a test, never inline in `customers.tsx`.
</Step>
<Step title="Never let territory widen sight">
Territory may only `and` onto `principalBookClause`. Any new exemption belongs in `territoryExempt`, the one definition three callers read.
</Step>
</Steps>
