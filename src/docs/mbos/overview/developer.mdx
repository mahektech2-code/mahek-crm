MBOS is an **Expo / React Native** app in `mbos-app/` (Expo SDK 57 per `mbos-app/package.json` — read the installed typings in `node_modules` before trusting any older note that says otherwise). It is a separate project: its own `tsconfig.json`, its own tests, and nothing in the Next.js app imports from it. The two meet only over HTTP, under `src/app/api/mbos/*`. The rules that both sides must agree on are either **shared numbers** (configuration sent down the pull) or **pinned by tests** that read both files as text.

## Map of the code

| Layer | Where | What lives there |
|---|---|---|
| Screens | `mbos-app/app/*.tsx` | One flat file per screen (expo-router). No nested routes: an address with a second path segment is never a screen |
| Root | `mbos-app/app/_layout.tsx` | Fonts, the `ErrorBoundary`, `SignedOutGuard`, the Stack, and side-effect imports that register the two background tasks |
| Shell | `mbos-app/src/components/shell/` | `AppFrame` (title bar, status strip, tab bar, + sheet), `Chrome.tsx` (`TabBar`), `routes.ts`, `TravelGate`, `AppLock`, `UpdatePrompt` |
| Local data | `mbos-app/src/data/*.ts` | Reads and writes against SQLite; every write ends in `enqueue` |
| Pure rules | `mbos-app/src/engines/*.ts`, `mbos-app/src/lib/*.ts` | No I/O, no clock — testable with `tsx --test` |
| Database | `mbos-app/src/db/schema.ts`, `index.ts`, `migrate.ts` | The SQLite schema as an ordered list of migration blocks |
| Sync | `mbos-app/src/sync/*.ts` | `api.ts` (HTTP + tokens), `queue.ts` (outbox), `engine.ts` (`syncNow`), `pull.ts` (`applyPull`), `trail.ts` (positions), `media.ts` |
| Native | `mbos-app/src/native/*.ts` | Permissions, location service, push, biometrics, OTA updates |
| Server routes | `src/app/api/mbos/*/route.ts` | `auth/login`, `auth/otp`, `auth/refresh`, `bootstrap`, `sync`, `positions`, `media`, `dictate/*`, `customer-account`, `order-products`, … |
| Server rules | `src/lib/actions/mbos.ts` | `mbosLogin`, `ingestSyncBatch`, `dispatchItem` and every `handle*` |
| Server reads | `src/lib/services/mbos-service.ts` | `runLoginChecks`, `checkDeviceBinding`, `authenticate`, `customerIdsInScope`, `buildBootstrap`, `buildPull` |

## The local database

SQLite through `expo-sqlite`. The schema is **one ordered array of migration blocks**; `PRAGMA user_version` records how many have run.

<Code file="mbos-app/src/db/schema.ts" symbol="SCHEMA_VERSION" />

<Callout kind="warn" title="Adding a block IS adding a migration">
`SCHEMA_VERSION` was once a literal and drifted: a block was added and the constant left one short, so `migrate()` returned before running it on every handset already in the field — while fresh installs were fine. Never reintroduce a literal. Statements are idempotent (`CREATE … IF NOT EXISTS`, and `alreadyApplied` tolerates a duplicate `ADD COLUMN`) so a phone that skipped two releases converges on the same schema.
</Callout>

<Callout kind="rule" title="The handset's schema is the wire contract">
`applyPull` inserts exactly the columns that arrive. A field the server sends that the handset has no column for used to throw and roll back the whole pull — the book, the prices, everything. `upsert` now drops unknown columns; `src/lib/mbos-wire.test.ts` reads both sides as text and pins it. Trim the payload to the handset, never widen the handset to the payload: an APK cannot be recalled.
</Callout>

## Access

- **Module:** <ModuleRef k="field.home" /> — the only module of the `field` app, `mobileOnly` in `src/lib/apps.ts`, so no launcher tile and no web route.
- **Authentication:** a bearer access token on every call but login; `authenticate` reads role, app access and whether the account is open from the database every time, so taking the app away takes effect on the next request.
- **Scope:** `customerIdsInScope` — the security clause (`principalBookClause`) ANDed with the territory clause. See [Customers](/docs/mbos/customers/developer).

## Changing the app safely

<Steps>
<Step title="Put the rule in an engine">
Anything that decides something goes in `mbos-app/src/engines/` or `src/lib/`, pure, with a test. `data/` files import SQLite at module scope and cannot be tested off a device.
</Step>
<Step title="Make it configuration, and publish it">
A number a manager might change goes in `src/lib/config/registry.ts` with a `Config` type entry, and must be in the set the pull publishes — the handset's `getConfig` falls back silently to its own default when a key never arrives.
</Step>
<Step title="Re-check it on the server">
A rule on the phone is a courtesy; the `handle*` function is the rule. Never trust a figure the handset computed (worked minutes, status, totals).
</Step>
<Step title="Ship server first">
The server must accept old payloads and send nothing an old build cannot hold. Then bump the handset version and release through the workflow — see [Releasing the handset app](/docs/platform/handset-release).
</Step>
</Steps>

|---|---|

| The login route comment speaks of five checks; the service runs four before device binding and calls the bootstrap the fifth | `src/app/api/mbos/auth/login/route.ts`; `mbos-service.ts` `runLoginChecks` |
