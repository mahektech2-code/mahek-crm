The Orders screen is ten tabs, each its own server module: nine built in `screens/sales.ts` (`orderList` for seven scopes, plus `batchCodes` and `orderDetails`) and the inbox in `screens/inbox.ts`. The Order-to-Delivery rules — the separate status words, whole-order billing, invoice change detection, duplicates and moving a line out — are pure in `engines/order-flow.ts`. Every list reads one function, `orderLines()`, so a line cannot be Ready on one tab and something else on another. The arithmetic is pure in `engines/sales.ts`; every write ends with `syncBookOrders`, which projects the change into MahekOne's order book (covered on [the order book page](/docs/erp/order-book/developer)).

## Prices

<Code file="src/lib/erp/screens/sales.ts" symbol="priceBook" collapsed />

`priceBook` resolves each party's list with `resolvePriceList` — the Accounts app's own rule, over `activeScopesAndLists` and `geographyOf` from `price-list-service.ts` — and never reads `customers.price_tag`. The order form carries the answer as fills, not data: the `priceList` header field is filled from `billing`, and each line's `rate` from `priceList` and `sku` (`otherwise: ""` clears it on a party or SKU with no rate). A header fill moves the line fields that read it, and `withFills` applies the same fills to a form that opens with its party picked ("Add to order", a drafted order).

`saveOrder` takes the typed rate only from a holder of `viewSalesRate`; otherwise, or where the box is blank, the list's rate. The discount is only ever typed, by a holder of `viewSalesAmounts`.

## Dispatch

<Code file="src/lib/erp/screens/sales.ts" symbol="verify" collapsed />

`verify` expands the ids to whole orders (`wholeOrders`), refuses an order with an unbilled live line, an invoice not `Approved`, or any line still gated by `scanGateFor`, then writes `vehicle_no` (upper-cased), `driver` and `dispatch_remark` with the dispatch. `openTransports` opens or joins the consignment and calls `assignTripsAtDispatch` with the vehicle. The Dispatch desk's **Confirm dispatch** calls this same bulk handler through `erpDispatchVerify` in `actions/erp-trace.ts`, after `requireErpWrite("orderDetails")`, so every rule here holds from both doors. `DISPATCH_PROMPT` is the one prompt both the row and the bulk bar ask.

## Access

- **Module:** <ModuleRef k="erp.orders" />. All seven tabs come with it; none is grantable alone.
- **Powers** read here: `viewSalesRate`, `viewSalesAmounts`, `viewCost` (columns and fields, via `visibleCols` / `withoutHidden` — values are stripped server-side), `approveParty` (Approved By Admin, and only while `erpOrdersLive()` is false), `verifyOrders` (Verify order, Send back for correction; told when an order is Ready to bill), `checkInvoices` (Approve / Reject invoice; told of new and changed invoices; refused on a bill whose `created_by_id` is the checker unless `ctx.administrator`). `notVerify` checks `ctx.administrator`.
- Every write is `requireErpWrite(<tab key>)`; a preview refuses all of them.

## Changing it safely

<Steps>
<Step title="Read orderLines, never re-query a line">
Every tab, the alerts and Ask the ERP read `orderLines()` / `detailRows()`. A screen with its own SQL for "is this line Ready" will disagree with the Dispatch desk.
</Step>
<Step title="Keep the arithmetic in engines/sales.ts">
And keep `calcs/sales.ts` as a preview only — the server recomputes everything on save.
</Step>
<Step title="Call syncBookOrders after every write that changes a line">
The CRM, targets and outstanding read the projection, not `erp_orders`. A write that forgets it leaves the order book stale until the next change to that order.
</Step>
<Step title="Withhold money server-side">
A new money column takes a `pw:` on its `Col` so `visibleCols` drops it and `withoutHidden` strips its value.
</Step>
</Steps>
