Everything MahekOne says about selling is read off one order book — the `orders` and `bills` the CRM, Accounts, targets and the owner's figures all share. The ERP keeps far more detail about an order than that book does: lots allocated, readiness, billing line by line, dispatch scans, the lorry. This page explains how the two meet: one switch, <Setting k="erp.orders.live" />, decides whether the ERP or the order sheet writes the book, and what everything downstream reads once it does. A second, <Setting k="erp.orders.partySheet" />, decides how long the Sales Party tab stays the party master after the order tabs have stopped.

## Why there has to be one book

<Callout kind="why">
Targets, the Call Log's reorder dates, the buying cycle, outstanding, collections and the owner's five KPIs are all computed from `orders` and `bills`. An ERP that kept its orders to itself would be a second order book that none of them could see: the godown would dispatch and bill, and the Call Log would go on ringing the customer to ask for the order they placed on Monday. And two sources writing the same book would count every order twice.
</Callout>

<Rule title="Exactly one author at a time">
Off, the ERP writes nothing into the book: the ERP runs on its own, and orders and bills keep arriving from the Taken Order and Order Details sheets. On, every ERP order is written into the book, and the order sheet's Order Details, Payment Status and Taken Order tabs are no longer read: the projection writes **no** customer, **no** order and **no** bill. A new party is created in Accounts → Add customer — the ERP creates none. The Sales Party tab is a different source with its own switch (below).
</Rule>

## What the switch changes

| | Off | On |
|---|---|---|
| Who writes `orders` and `bills` | The order sheet projection | The ERP, after every change to an order |
| A Pending customer's order | The ERP's own "Approved By Admin" (the approve-party power) | The Accounts approval queue, like any order needing a check |
| Who is held off the Call Log for an open order | Open lines on the Taken Order tab | ERP lines not cancelled and not yet dispatch-verified |
| Targets, buying cycle, outstanding, KPIs | Read the sheet's orders | Read the ERP's orders |
| The Order Details, Payment Status and Taken Order tabs | Read every half hour | Not read — retired (below) |
| A customer typed into Order Details | Created by the projection | Not created |
| A lead's second order | Converts it on a CRM call, a handset order or an Accounts approval | An ERP order converts it too |
| A customer's product history and frequent products | The sheet's orders | The sheet's history and the ERP's orders |

## The Sales Party tab has its own switch

<Rule title="The party master can outlive the order tabs">
<Setting k="erp.orders.partySheet" /> is on by default. On, the Sales Party tab is still read every half hour and fills each party's salesperson and back-office seats, deactivations, and any phone, GST, credit days or price list nobody has typed into MahekOne. Off, the tab is retired: it is no longer read or published, and all of that is kept in MahekOne — Accounts → Add customer, the customer record, the account-manager dialog, ERP → Sales parties. The two switches are independent.
</Rule>

| `erp.orders.live` | `erp.orders.partySheet` | Order tabs | Sales Party tab | The half-hourly publish |
|---|---|---|---|---|
| Off | On | Read | Read | Customers, orders and bills from Order Details, then the party master |
| On | On | Retired | Read | The party master only |
| On | Off | Retired | Retired | Retired — nothing is published from the workbook |
| Off | Off | Read | Retired | Customers, orders and bills from Order Details only |

<SettingsTable keys={["erp.orders.live", "erp.orders.partySheet"]} />

<Rule title="A retired tab is not read, whoever asks">
The droplet's schedule, the Admin Console and a terminal all come through one job runner, and it answers a retired read with the reason instead of running it — it still records a job run carrying that sentence, so the schedule keeps getting a success and the job history says why nothing happened. Once the ERP takes the orders, Admin Console → Sheets and Accounts → Sheet import show a banner and draw their import buttons disabled with the reason. The Command Centre shows a retired source as **Retired · last read … ago** — never *Stale*, with nothing to run — and Admin Console → Integrations lists it as **Retired**.
</Rule>

<Callout kind="note" title="Nothing the sheet wrote is deleted">
Retiring a tab deletes none of its staged rows or the orders and bills it published. Bill detail, delivery-party linking and the price-list variance report still read them for the months the sheet was the source.
</Callout>

## An ERP order in the book

<Flow caption="From ERP order lines to one order and one bill" chart={`
flowchart TD
  L["ERP order lines<br/>one order number, many SKUs"] --> S{"Every line cancelled?"}
  S -- "Yes" --> C["Book order: cancelled<br/>an unpaid bill is removed"]
  S -- "No" --> D{"Accounts declined it?"}
  D -- "Yes" --> X["Book order: declined"]
  D -- "No" --> P{"A live line's customer is Pending<br/>and Accounts has not approved?"}
  P -- "Yes" --> PA["Book order: pending approval<br/>in the Accounts queue"]
  P -- "No" --> V{"Every live line<br/>dispatch-verified?"}
  V -- "No" --> CF["Book order: confirmed"]
  V -- "Yes" --> T["Book order: dispatched,<br/>in transit or delivered<br/>from the transport stage"]
  L --> B{"Any live line<br/>dispatch-verified?"}
  B -- "Yes" --> BL["One bill: stated, owed<br/>value of the lines that left"]
  B -- "No" --> NB["No bill<br/>(an unpaid one is removed)"]
`} />

<Rule title="One order number is one order, and one bill">
However many lines and SKUs an ERP order has, the book holds one order for it, keyed `ERP-` and the order number, and — once anything has left — one bill keyed separately. The keys are the ERP's own, never the sheet's, so the sheet projection can never overwrite them.
</Rule>

<Rule title="The book's copy is rewritten whole, never edited">
After any ERP write that can change an order's lines, status, value or dispatch, the book's copy of that order is rebuilt from the ERP's lines. It is a projection, so it cannot drift into a second opinion; an edit made to it in Accounts would be overwritten.
</Rule>

### What the order says

| Field | From the ERP |
|---|---|
| Customer | The billing customer; a different delivery customer is kept beside it |
| Taken by | Whoever created the ERP order |
| Ordered on | The ERP order date, at 10:00 in the business's time zone |
| Lines | Each live line: SKU, cans, rate and its value |
| Value | Per line: amount (cans, or litres for a drum, × rate) less discount, plus freight, plus GST — summed |
| Net value | Amount less discount, before freight and GST |
| Credit days | The billing customer's own credit term |
| Expected dispatch | The earliest planned dispatch date on its lines |

### Where the order stands

The status comes from the ERP's lines, with two decisions that the ERP cannot undo:

- **Declined by Accounts** stays declined. Nothing the godown does afterwards turns a declined order back into a sale.
- **Pending approval** holds while any live line's customer is Pending and Accounts has not approved the order.
- Once every live line is dispatch-verified, the transport record's material stage decides between **dispatched**, **in transit** and **delivered** ("Close - Received to Party" is delivered).
- Otherwise the order is **confirmed**.

<Callout kind="note" title="Only a Pending customer's order goes to Accounts">
An ERP order from an **active** customer is confirmed in the book as soon as it is taken, and counts as a sale from then on. Unlike an order logged on a CRM call, it does not wait in the Accounts queue: in the ERP the customer's activation by an admin or the office is the check, and Accounts sees only the orders of customers who have not had it.
</Callout>

## The bill

<Rule title="A bill appears when goods leave, and it is owed">
The first time a line of the order is dispatch-verified, one bill is written for the order: its value is what has left so far, its date the earliest dispatch date among those lines. It is **stated** — a real invoice the business raised, owed until money is recorded against it, and therefore on outstanding, aging and the collections worklist.
</Rule>

<Callout kind="money">
Since October 2026 a sheet bill lands owed from its due date too, unless the sheet's Payment Status tab says the money was received. An ERP bill is owed for a stronger reason: the ERP itself billed and dispatched it, and there is no Payment Status tab to say otherwise. Payment against it is recorded and confirmed in Accounts exactly as for any bill; see [Bills](/docs/crm/bills) and [Outstanding](/docs/crm/outstanding).
</Callout>

<Rule title="A bill number is never taken from another bill">
The bill takes the Tally number the order desk entered. Bill numbers are unique across MahekOne, so where that number is already held — usually by a bill the sheet wrote — it falls back to the Tally number followed by `/ERP` and the order number, then to `ERP-` and the order number. It is the same fall-back chain the sheet itself uses.
</Rule>

<Rule title="An unpaid bill follows its lines; a paid one stays">
If every verified line is un-verified or cancelled again, a bill with **no** money recorded against it is removed with the lines that made it. A bill with any payment against it is never removed by the ERP.
</Rule>

After every rewrite, the buying cycle, outstanding and the follow-up stage are recomputed for each customer the order touched.

## Accounts and a Pending customer

<Callout kind="why">
In Mahek Plus a pending party's order was approved by the admin inside the ERP. With the ERP live, Accounts already has a queue for exactly this decision, so the ERP's own button is withdrawn: one door means an order cannot be approved twice, or approved in one place and declined in the other.
</Callout>

## The Call Log hold

<Rule title="A customer with an open ERP order is not chased for one">
With the switch on, a customer is held off the Call Log's order chasing while any ERP line billed to them is neither cancelled nor dispatch-verified, and released when the last one leaves. Every customer is rewritten on every pass, so a hold can only say what the ERP currently says — the same rule the Taken Order tab followed. See [the Call Log](/docs/crm/call-log/how-it-works).
</Rule>

The hold is rebuilt **every hour**, by a step of the hourly pass that reads whichever source is current — the staged Taken Order rows while the sheet takes the orders (the Taken Order sync also rebuilds it then, every half hour), the ERP's open lines once it does. The ERP book sync rebuilds it too. It is not rebuilt by each ERP save, so a customer can be rung for up to an hour after ordering.

## Going live

Every step here is somebody's to perform; none of it happens on its own.

<Steps>
<Step title="Stop the sheet">
The order desk stops typing orders into the Taken Order sheet at an agreed time.
</Step>
<Step title="Close the history copied from the sheet">
A one-off developer step — no screen does it. Lines the Taken Order tab still had in flight, copied into the ERP with source *sheet*, are converted to source *erp*, because the book writes only the ERP's own lines. Copied lines the sheet showed **Ready** and **Done** whose Order Details row carries no dispatch date are marked dispatched: the hold reads every ERP line not cancelled and not dispatch-verified, and the import marked a copied line verified only where Order Details gave it a dispatch date — so left alone, those would hold their customers for good.
</Step>
<Step title="Turn the switch on">
<Setting k="erp.orders.live" /> in Admin Console → Settings → ERP → Production & orders.
</Step>
<Step title="Run the ERP book sync once">
`npm run jobs -- erp-book-sync`. It writes every ERP order already in the ERP into the book (two hundred at a time) and rebuilds the Call Log holds. While the switch is off the job writes nothing and says so.
</Step>
<Step title="Retire the Sales Party tab, when the office is ready">
Turn <Setting k="erp.orders.partySheet" /> off once seats, deactivations and contact details are kept in MahekOne rather than on the tab.
</Step>
<Step title="Trim the droplet's schedule">
Tidying rather than urgent, since a retired mode answers successfully and does nothing. The planned trim of `deploy/sheet-sync.sh` leaves the half-hourly cycle with only the punch-out reminders and the nightly with only `sync nightly`, relaxes its `SYNC_OWNER_EMAIL` check, and changes the `grep -c field-activity` check at the end of `ship-sync-schedule.yml` to match. While <Setting k="erp.orders.partySheet" /> is on, `parties` and `project` must stay in the cycle — they are what publishes the party master.
</Step>
</Steps>

<Callout kind="warn">
Never turn the switch on while the team is still typing orders into the sheet. Orders taken on the sheet before the switch stay in the book as they were; the ERP's own orders are added beside them under their own keys.
</Callout>

## Who can do what

| Act | Who |
|---|---|
| Turn the switch on or off | Whoever may edit ERP settings in the Admin Console |
| Approve or decline a Pending customer's order (live) | Accounts, from Order approvals |
| Approve a Pending customer's order (not live) | Holders of the ERP's "Approve orders from pending customers" power |
| Edit an order's lines, billing, dispatch | The ERP's Orders and Dispatch screens — never the book |

## Where the code and the intent disagree today

- The Call Log hold is not rebuilt when an ERP order is saved, only by the hourly pass and the ERP book sync, so a customer can be chased for an order they placed for up to an hour.
- The hold reads every ERP line not cancelled and not dispatch-verified, including lines copied in from the sheet, which the import marked verified only where Order Details gave a dispatch date; only the hand-run cut-over step above keeps the rest from holding their customers permanently.
- Before an order's billing details exist, its value in the book assumes 18% GST on every line; the GST actually billed replaces it only once the line has billing details. The 18% is written in the code rather than taken from a setting.
- The ERP book sync has no button in the Admin Console; on a deployment without shell access it cannot be run on go-live day.
