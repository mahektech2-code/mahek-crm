The ERP is **data-driven**. One registry (`lib/erp/registry.ts`) lists every screen and its tabs; one context (`erpContext`) says who the person is inside the ERP; one dynamic route (`app/erp/[slug]/page.tsx`) draws any list screen from a **screen module** in `lib/erp/screens/`; and every write from a list screen goes through four server actions in `lib/actions/erp.ts`. The bespoke screens — dispatch, trace, logistics, Petty Cash, the Quotation manager, stock inquiry, the PO print, labels, settings — live in their own route folders, and the ones that write have their own action files beside `erp.ts`. This tab is the map; each area's page has its own developer tab.

The engines in `lib/erp/engines/` perform **no I/O**, like every engine in MahekOne. The form previews a figure with the same function the server stores it with (`calc` names on derived fields map to `lib/erp/calcs/`), so the preview and the save cannot disagree.

## A screen says a thing once

The generic list (`_ui/list-screen.tsx`) and record dialog (`_ui/record-dialog.tsx`) leave out what would only repeat:

| Repeat | What happens | Where |
|---|---|---|
| A flag reading the same as the row's status | Not drawn | `flagsBesideStatus` in `_ui/badge.tsx` |
| The grouped-by column, while grouped | Dropped from the rows; the group header says it | `lineCols` in `list-screen.tsx` |
| Search, group and columns on a list with no rows | Toolbar not drawn | `list-screen.tsx` |
| A record field with a column's label | Takes the column's place in the record | `record-dialog.tsx` |
| Columns a panel already shows | Listed in the panel's `covers`, left out of the record's Details tab | `ListRow.panel.covers` in `lib/erp/ui.ts` |

A `noDataLine` is drawn as a heading (its first sentence) and a muted explanation (the rest), so write the first sentence to stand on its own.

## The sidebar badges

A badge for a screen with tabs is the sum over `erpKeysOf(screen)` in the layout, and each tab draws its own figure through `screenTabs`: Logistics' LR desk, On the road and Customer messages each carry their own count (LRs to attach, calls due, messages to send), and the sidebar shows their sum.

## Access and modules

- **Modules:** one per built screen, e.g. <ModuleRef k="erp.dashboard" />, <ModuleRef k="erp.stock" />. Tabs are not modules.
- **No capabilities.** The ERP's row in `capability-matrix.ts` is empty on purpose; decisions are ERP **powers** (`lib/erp/powers.ts`). See [Access and designations](/docs/erp/access-and-designations/developer).

## Adding a screen safely

<Steps>
<Step title="Declare it in the registry">
Add it to its group in `ERP_GROUPS` with `built: false` while it is being written — an unbuilt screen is not a module, so nothing can be granted onto a page that does not exist. Its key becomes `erp.<key>` and is a grant: never rename it.
</Step>
<Step title="Write its module">
A `ScreenModule` in `lib/erp/screens/`, registered in `screens/index.ts`. Mark money columns with `pw`, run every list through `visibleCols`/`withoutHidden`, and give every refused action a `why`.
</Step>
<Step title="Check the power inside every handler">
The four doors check the screen; the handler checks the power. A hidden button is not a permission.
</Step>
<Step title="Consume stock only inside a transaction that locks the lot">
`lockLot`, then read stock with the transaction (`rmLots(tx)` etc.), then refuse with `refuse(...)` inside `inTx`.
</Step>
<Step title="Flip built, add a dashboard tile and a badge from the same function">
A tile and a badge that count with different queries will disagree.
</Step>
<Step title="Claim the new module in the docs registry">
`src/docs/coverage.test.ts` fails until a documentation page claims it.
</Step>
</Steps>
