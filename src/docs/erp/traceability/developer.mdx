Traceability is a bespoke, read-only route. `lib/erp/traceability.ts` resolves a code and walks the chain with raw SQL; the pure pieces (ids, code cleaning, which refill lots a box holds) are in `engines/trace.ts`; `trace-links.ts` is the one place a link into the trace or the label sheet is spelled. A second, narrower trace — `lib/erp/trace.ts`, from a bill — serves the complaint panel and Ask the ERP. The only writes nearby are the label-printed stamp and the dispatch desk, both in `actions/erp-trace.ts`.

| Layer | File | What lives there |

## Changing it safely

<Steps>
<Step title="Keep it read-only">
Nothing under `traceability.ts` writes. A fix to data belongs on the screen that owns it.
</Step>
<Step title="Say what is missing">
A new stage that can fail to resolve must push a sentence onto `missing`.
</Step>
<Step title="Spell links through trace-links.ts">
Every screen links in through `erpTraceHref` / `erpLabelsHref`; a hand-built URL drifts the day a query key changes.
</Step>
<Step title="Change both traces, or merge them">
`trace.ts` and `traceability.ts` walk the same chain. A new production stage has to be added to both.
</Step>
</Steps>

## Known gaps, with file references

| Gap | Where |
|---|---|
| A code made only of digits resolves as an order number before it is tried as a lot or a Tally bill number | `traceability.ts` `resolveTrace` |
| Two independent chain-walkers; the complaint trace has no SFG QC step and does not split a boundary box | `trace.ts` `traceFromOrders`; `traceability.ts` `backward` |
