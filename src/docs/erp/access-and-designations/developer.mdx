ERP access is resolved **once per request** by `erpContext` (`lib/erp/access.ts`, wrapped in React `cache`): the level on the `erp` grant, the screens it opens (with every tab of each), the powers, the godowns, the designation and its department. The layout, the page and every write ask that same object. Designations are pure arithmetic in `lib/erp/designations.ts`, applied by `lib/actions/erp-designations.ts`; the Access dialog writes through `setAccess` and the shared writers in `lib/services/access-writes.ts`.

## Permissions

- **Modules:** <ModuleRef k="erp.settings" /> and <ModuleRef k="erp.dashboard" /> are always open (`ERP_ALWAYS_OPEN`, mirrored into `ALWAYS_OPEN_MODULES` so the Access screen draws them as always on); <ModuleRef k="erp.videos" /> is granted like any other screen.
- **Designations and powers** are changed only by a platform administrator (`requirePlatformAdminUser` in `erp-designations.ts`; the Access dialog's own guard in `setAccess`).

## Changing it safely

<Steps>
<Step title="A new power">
Add it to `ERP_POWERS`, give it a label and a source sentence in `ERP_POWER_LABEL` (the registry test fails otherwise), a sentence in `powerRefusal`, and check it inside the handler of every write it guards — never only in the screen.
</Step>
<Step title="A power that reveals a column">
Put `pw` on the column and let `visibleCols`/`withoutHidden` drop it. Never blank a value in the browser.
</Step>
<Step title="A new always-open screen">
Add it to `ERP_ALWAYS_OPEN`; `ALWAYS_OPEN_MODULES` and `grantableModules` follow.
</Step>
<Step title="Seeding designations">
Do it in a migration that names only real `erp.<key>` modules and real powers — `designations.test.ts` reads the seed and refuses anything else.
</Step>
</Steps>
