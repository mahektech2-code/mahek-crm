A complaint is a row in `complaints` with an opening line in `complaint_status_history`, photographs in `attachments`, and an SLA deadline computed from configuration. One writer, `createComplaint`, is shared by the Complaints dialog and the ERP's "Raise a customer request"; three other paths — the call panel, the collections *Dispute raised* outcome and the handset — insert complaints themselves. Reads, status changes, priority and resolution live in `worklist-services.ts`; the hourly job escalates deadlines that pass.

## The deadline job

`runHourly` selects complaints with `sla_due_at` in the past, `resolved_at` null and `sla_escalated_at` null, stamps `sla_escalated_at`, and notifies managers and admins. It runs once per complaint.

## Access

- **Module:** <ModuleRef k="crm.complaints" />.
- **Scope:** `listComplaints` is narrowed to the reader's book; status and priority changes run `customerOfComplaintInScope`.
- **Photographs** are read through `/api/attachments/[id]`, which follows the parent complaint's customer scope.

## Changing it safely

<Steps>
<Step title="Write through createComplaint">
A new door that raises complaints should call `createComplaint` (passing its transaction) rather than insert — that is how the deadline and the opening history line are guaranteed.
</Step>
<Step title="Labels in, values stored, labels out">
Categories a person picks are configuration (`complaints.categories`); stored values are the enum. Map with `categoryValue` and back with `categoryLabel` — never show a stored enum.
</Step>
<Step title="Finishing needs the capability, both ways">
Keep the `FINISHED_COMPLAINT` check in `changeComplaintStatus` for any new status.
</Step>
<Step title="Photographs through the picker">
`ACCEPTED_IMAGE_TYPES` and `attachments.maxPerComplaint`; never a literal accept list.
</Step>
</Steps>

## Known gaps, with file references

| Gap | Where |
|---|---|
| Four writers: only the dialog and the ERP use `createComplaint`; the call path, the collections dispute and the handset insert directly | `interaction-service.ts`, `payment-followup-service.ts` (dispute branch), MBOS sync |
| `logComplaint` does not run `assertCustomerInScope` on the customer it is given | `actions/crm.ts` `logComplaint` |
| Images travel in the server action body (default 1 MB limit) | `actions/crm.ts` `logComplaint` (`images?: File[]`) |
| `reassignComplaint` writes `assigned_to` with raw SQL after the status change, outside its transaction | `actions/crm.ts` `reassignComplaint` |
| The deadline job and the breach flag read `resolved_at`, not the status | `jobs.ts` `escalate-complaint-sla`; `worklist-services.ts` `listComplaints` (`slaBreached`) |
| The badge filters by `cu.owner_id` rather than `ASSIGNED_TO_SQL` | `queries.ts` `crmBadgeCounts` |
