Configuration is a **registry** of typed definitions (`lib/config/registry.ts`), **stored values** layered over its defaults (`app_settings`), one **cached read** (`getConfig`), and one **write path** (`updateSettings`) reached from the Admin Console's settings editor through `updateConfigSettings`. Which page, tab and group a setting is drawn on is decided by pure placement rules. The Help Center is a read of `help_articles`; call scripts are the same rows, rendered with placeholders filled in the call panel. Everything below is cut from the source this deployment was built from.

## Changing it safely

<Steps>
<Step title="A new setting is three edits">
A definition in `SETTINGS` (type, default, bounds, description), an entry in the hand-typed `Config` type, and a placement (a `PRESENTATION` entry or a rule). Missing the `Config` entry breaks only the server build.
</Step>
<Step title="Never default to null">
`app_settings.value` is NOT NULL jsonb. A null default breaks every writer and every integration test.
</Step>
<Step title="Relationships go in checkConsistency">
If two settings state one fact, add the check there so the editor flags it and the server refuses a new contradiction.
</Step>
<Step title="Moving a shipped default is a migration that respects choices">
Update only rows where `updated_by_id is null` and the value is still the old default.
</Step>
<Step title="A script is an article">
Write call scripts as `help_articles` of type `call_script`; never put script text in a component.
</Step>
</Steps>
