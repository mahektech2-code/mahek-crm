Close/Reopen is a **flag on the customer row**, raised by two request actions and cleared by two decide actions, with one unscoped read (`listCustomerStatusRequests`) rendering both directions as one queue. There is no requests table: the pending state, the reason, who asked and when all live on `customers`. The status the decision writes, `deactivated`, is the one value of `customer_status` that the inactivity engine reads but never writes.

## The four actions

### Asking to close

`requestDeactivation` takes ids and a reason. It resolves scope and — before writing — selects the ids through `scopedToUsers(scopedUserIds(ctx.scope))`; any shortfall refuses the whole call with `not_permitted`. It then stamps the flag, the reason, `deactivation_requested_by_id` and `deactivation_requested_at`, and inserts a `notifications` row per user whose `users.role` is `manager` or `admin`.

<Code file="src/lib/actions/crm.ts" symbol="requestDeactivation" collapsed />

### Deciding a close

Approval sets `status_decided_at`, which is what keeps the party sheet's *Deactive* column from restating the status later. Rejection clears the flag **and** `deactivation_reason`.

<Code file="src/lib/actions/crm.ts" symbol="decideDeactivation" collapsed />

### Asking to reopen

Filters the selection to rows already `deactivated` and flags only those; returns `conflict` if none qualify. Notifies through `notifyUsers` with `href: "/crm/status-requests"`.

<Code file="src/lib/actions/crm.ts" symbol="requestReactivation" collapsed />

### Deciding a reopen

Approval sets `active`, nulls every deactivation column and the reactivation request, and **also** sets `status_decided_at` — clearing `deactivation_reason` destroyed the only evidence the projection used to read, so without the mark the next sync re-closed the account. `recomputeInactivity` then moves a long-quiet customer straight to `inactive`.

<Code file="src/lib/actions/crm.ts" symbol="decideReactivation" collapsed />

## The read

One `union all` of the two flags, oldest first with undated (pre-asker-column) requests last. It is **not scoped**: a request is work for whoever decides it, and narrowing to the decider's book would hide most of them. It is not aliased because `ASSIGNED_TO_SQL` names `customers` directly.

## Changing it safely

<Steps>
<Step title="Keep 'deactivated' out of every engine">
No recompute, sync or job may write or clear `deactivated`. If a new automatic path needs to close accounts, route it through a request a person decides.
</Step>
<Step title="Set status_decided_at on every human status write">
Any new action that changes a customer's status must stamp it, or the party projection will overwrite the decision on the next pass.
</Step>
<Step title="Gate deciding on the capability, never on isManager">
The route, the sidebar, the badge and the actions all ask `customer.deactivate`. A screen that draws decide buttons from `isManager` will offer buttons the server refuses.
</Step>
<Step title="Re-run inactivity after a decision">
Both decide actions call `recomputeInactivity(customerId)`; keep that, or a reopened quiet customer reads as active and a closed one keeps its watch row.
</Step>
<Step title="Add a Journey 5 test">
Every behaviour on this page has an integration test; a new rule without one is a rule nobody can tell has broken.
</Step>
</Steps>
