Samples are rows in `mbos_samples` — the same table the handset writes — worked from the CRM's own desk at `/crm/samples`. Every CRM write is in `actions/lead-samples.ts` and begins with one loader that checks scope and the state machine; the review chase is a pure engine run hourly; the seven feedback answers are their own table, one row per sample. Every block below is cut from the source this deployment was built from.

## Changing it safely

<Steps>
<Step title="A new state is a new edge in ALLOWED, and nowhere else">
Add it to `mbos_sample_state` (hand-written migration, cast enum literals `::text`), to `SampleState`, to `ALLOWED`, to `STATE_WORDS`, and to the handset's own machine.
</Step>
<Step title="Never default one date from another">
`received_at` is the shop's; `delivered_at` the carrier's. A new date gets its own column and its own assertion.
</Step>
<Step title="Chases close, they do not delete">
Use `closeNurtureTasks` with a sentence. A deleted chase loses the record that the parcel was slow.
</Step>
<Step title="Keep the rejection check and the derivation on the same three fields">
If you change which fields feed `rejection_reason`, change the validation with it, on both the CRM and the handset.
</Step>
</Steps>

## Known gaps, with file references

| Gap | Where |
|---|---|
| CRM approval does not move the lead to Negotiation; the handset's does | `actions/lead-samples.ts` `recordSampleFeedback`; `actions/mbos.ts` `afterSampleVerdict` |
| Handset receipt raises a single `mbos.samples.reviewAfterDays` task as well as the hourly chase ladder | `actions/mbos.ts` (sample review task); `mbos-jobs.ts` `chaseSampleReviews` |
| The handset review task's due date is `now + days × 86 400 000 ms`, not working days | `actions/mbos.ts` |
| `chaseSampleReviews` skips a sample with neither a lead manager nor a salesman, silently | `mbos-jobs.ts` |
