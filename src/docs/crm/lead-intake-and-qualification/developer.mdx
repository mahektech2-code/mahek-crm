Intake and Qualification are two lead modules (<ModuleRef k="crm.lead-intake" /> and <ModuleRef k="crm.lead-qualify" />), each guarded by its own folder layout and each rendering a shared page from `src/components/leads/pages/`. Raising a lead has **one writer**, `captureLead`, used by the form, bulk intake and the enquiry screen. Qualification's screens are reads over the gate engine; every write on them is an existing lead action, and every stage change goes through `advanceLeadStage`.

## The verification call and validation answers

`recordLeadValidationCall` (`lead.verify`) writes one row per call to `mbos_lead_validations` — the same table the handset writes — using `VERIFICATION_COLUMNS` in `lead-labels.ts` as the one statement of which answer lands in which column. `not_qualified` requires a note and closes the lead through `advanceLeadStage` with the verification-failed code. A desk request is then settled by `settleProspectRequest`.

## Changing it safely

<Steps>
<Step title="One way to raise a lead">
Any new door (an import, an API) calls `captureLead` or `captureLeadBatch`. A second insert path would skip the duplicate guard, the foot-of-ladder rule, the distributor link and the timeline row.
</Step>
<Step title="Never make a capture field required to fix a gate">
If the gate needs something, it asks at the rung. Capture stays four fields.
</Step>
<Step title="Validation answers are a row, not columns on the lead">
Add a confirmed answer as a column on `mbos_lead_validations`, map it in `VERIFICATION_COLUMNS`, and add it to `disagreementsIn` if both sides answer it.
</Step>
<Step title="Keep counts live">
Visit counts stay `count(*)` over `mbos_visits`; numbers beside parameters get `::int`.
</Step>
</Steps>
