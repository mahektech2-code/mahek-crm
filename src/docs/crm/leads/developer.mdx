Lead Management is **one workspace mounted twice**. The screens live in `src/components/leads/pages/*` and take a `workspace` prop (`"crm"` or `"sales"`); the CRM routes under `src/app/crm/leads/**` are thin files that pass `workspace="crm"`. The rules live in two pure engines — the **ladder** (what comes next) and the **gates** (may we) — and every stage move goes through one service function that writes an append-only transition row. Every block below is cut from the source this deployment was built from.

<Callout kind="rule">
The ladder and gate engines perform **no I/O and read no clock**. The handset compiles the same files so a salesman with no signal sees the same missing list the server would refuse on. Anything that needs configuration or the database — the override switch, reason-code validation, the parked-from rung — is settled in `evaluateLeadStageMove`, never inside the engine.
</Callout>

## A stage move, end to end

<Flow caption="advanceLeadStage — one lead, one rung" chart={`
sequenceDiagram
  autonumber
  participant UI as Record / bulk bar
  participant A as actions/leads.ts
  participant S as lead-service.ts
  participant G as engines/lead-gates.ts
  participant DB as Postgres
  UI->>A: advanceLeadStage(customerId, to, reasonCode?, override?, nextAction?, hold?)
  A->>A: zod parse, requireCapability("lead.work")
  A->>S: reachableLead() — assertLeadInScope
  A->>S: leadGateInput(lead) — counts, sample state, verification, qualification
  A->>S: evaluateLeadStageMove(lead, gate, to, reason, override, canOverride)
  S->>G: gateTo(gate, to)
  G-->>S: open / missing conditions
  S-->>A: passed · overridden · reverted, or a refusal code
  A->>S: applyLeadStageMove(decision, expectFrom)
  S->>DB: ONE transaction — lock the row, INSERT lead_stage_transitions,<br/>UPDATE customers (stage, since, next action, hold, conversion),<br/>cancel tasks on Lost, timeline event, notification, audit_log
  S-->>A: stage, promoted
  A-->>UI: "Moved to …" or "… is on the book" 
`} />

`expectFrom` is the optimistic lock: the row is re-read `for update` and a lead that moved since the screen drew it throws `StageAlreadyMoved` rather than being moved twice.

## Changing it safely

<Steps>
<Step title="A new rung goes in the ladder, the enum and the band map together">
Add it to `LeadStage` and `mbos_lead_stage` (hand-written migration), to the right ladder array, and to `bandOf`. The band test fails until you do.
</Step>
<Step title="Its conditions go in conditionsToEnter, keyed by destination">
Read a stored value, not a tick. Write `says` as an instruction. The handset compiles this file, so no imports beyond `lead-labels` and `lead-ladder`.
</Step>
<Step title="Never add a second path that writes lead_stage">
Every move — record, bulk, handset, calling desk conversion — goes through `evaluateLeadStageMove` + `applyLeadStageMove`. A direct `update customers set lead_stage` skips the gate, the transition row and the timeline.
</Step>
<Step title="Reason lists are settings">
A new coded list is a structured `leads.*` key in `registry.ts` with a `Config` type entry, defaulted from `lead-labels.ts`. Store the code; resolve the label with `labelOf`.
</Step>
<Step title="Conversion stays in lead-conversion-service">
If a new order path appears, call `convertLeadOnSecondOrder` from it. Count orders with `orderCountsSql`, never `status <> 'cancelled'`.
</Step>
</Steps>
