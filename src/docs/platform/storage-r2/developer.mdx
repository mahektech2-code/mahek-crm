The attachment subsystem is one service (`attachment-service.ts`) over one storage interface (`FileStorage` in `src/lib/storage.ts`) with two backends: **Postgres** (`attachment_bytes`, the default) and an **S3-compatible bucket** (Cloudflare R2 in production, signed by hand in `s3-signing.ts`, no SDK). The backend is chosen once, at module load, from environment variables. Bytes are only ever read back through `/api/attachments/[id]`, which asks `canRead` first. The handset has its own upload door (`/api/mbos/media`) that lands in the same table.

### Choosing the backend

<Code file="src/lib/storage.ts" symbol="s3Config" collapsed />

| Variables set | Backend |
|---|---|
| None of the below | Postgres |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT` (already there for backups) **and** `R2_ATTACHMENTS_BUCKET` | R2, region `auto` |
| `R2_*` with the bucket in the endpoint's path and no `R2_ATTACHMENTS_BUCKET` | R2, bucket from the path |
| `S3_BUCKET` or `S3_ENDPOINT` (plus `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, optional `S3_REGION`) | That store, overriding every `R2_*` name; region defaults to `us-east-1` |
| Bucket resolves to the same name as `R2_BUCKET` | **Refused** with a console error; Postgres is used |

<Callout kind="warn" title="R2's two particulars">
The region is the literal word `auto`, and `R2_ENDPOINT` carries the account id and **not** the bucket (backup.sh reads the same variable). Both mistakes produce a bare 403 or 404. Run `npm run check:storage` against the target environment before relying on it — it prints the backend and which of upload, read and delete failed.
</Callout>

### Reading falls back; removing removes from both

`s3Storage.read` asks the bucket and, on anything but success, reads `attachment_bytes` — so everything uploaded before the switch keeps opening. `s3Storage.remove` deletes from the bucket (a 404 counts as success) and then from `attachment_bytes`. Nothing migrates bytes between backends; `attachments.stored_ref` is the key in whichever store it was written to (`attachments/<id>`).

`attachment_bytes` is created by `drizzle/0011_attachment_bytes.sql` and is **not declared in `schema.ts`**: three columns, `ref` (primary key), `bytes` (`bytea`) and `created_at`. It is a separate table so that listing attachments never drags bytes through the pool.

Rules worth knowing before adding a parent type:

- **No customer behind it** (feedback, documents, courses, selfies, travel legs, expenses, price lists, ERP, HRMS, payouts) needs an explicit branch. The fall-through, `customerBehind`, looks the id up as a call — which is how every selfie once answered 404.
- **Sales evidence asks the module first, then `managerScope`.** `managerScope` alone is vacuous ("national") for anybody without a region row; asking `canOpenModule` for `sales.attendance` (selfies), `sales.travel`/`sales.expenses` (legs), or `sales.expenses`/`sales.exceptions` (expenses) first stops one salesman fetching another's photograph by id.
- **Not-allowed and not-found are identical**, so ids cannot enumerate customers.

## Removal and sweeps

<Code file="src/lib/services/attachment-service.ts" symbol="removeAttachment" />

<Code file="src/lib/services/attachment-service.ts" symbol="sweepOrphans" />

<Code file="src/lib/services/attachment-service.ts" symbol="sweepAttendanceSelfies" />

| Sweep | Runs | Selects | Does |
|---|---|---|---|
| `sweepOrphans` | Nightly (`sweep-orphan-attachments` in `runNightly`) | `parent_id is null` and uploaded before <Setting k="attachments.orphanCleanupHours" /> hours ago — **any status** | Deletes bytes from both stores, marks `removed` |
| `sweepAttendanceSelfies` | Hourly (from `mbosHourly` in `src/lib/mbos-jobs.ts`) | `parent_type = 'mbos_attendance'`, `available`, uploaded before <Setting k="mbos.attendance.selfieRetentionHours" /> hours ago | Deletes bytes, marks `removed`, **keeps** the parent and every reference on the attendance day |

Both delete bytes before updating the row, so a crash leaves a live row over missing bytes (a 502 somebody will notice) rather than a `removed` row over bytes nothing will ever tidy.

## Changing it safely

<Steps>
<Step title="A new parent type is three edits">
The `attachment_parent` enum value (in its own migration — a value cannot be used in the transaction that adds it), the `ParentType` union or `MBOS_PARENTS` entry, and a `canRead` branch.
</Step>
<Step title="Never serve a stored URL">
Objects are private; bytes go out through `/api/attachments/[id]` only. Do not add an ACL header to uploads.
</Step>
<Step title="Prove the store before switching">
`npm run check:storage` with the target environment's variables.
</Step>
<Step title="Never point attachments at R2_BUCKET">
The backup bucket's lifecycle rules delete old objects.
</Step>
</Steps>

## Known gaps

| Gap | Where |
|---|---|
| `removeAttachment` nulls `parent_id`, and `sweepOrphans` selects `parent_id is null` regardless of status — so a removed file's bytes are deleted after the orphan window, contrary to "the bytes go only when retention says so" | `attachment-service.ts` `removeAttachment`, `sweepOrphans` |
| `attachments.retentionDays` is never read | `src/lib/config/registry.ts` |
| `canRead` returns false for any status other than `available`, so the route's 410 "This file has been deleted" branch is unreachable — a swept selfie answers 404 | `attachment-service.ts` `canRead`; `src/app/api/attachments/[id]/route.ts` |
| The comment above `fileStorage` still describes a Vercel Blob backend and says reads of old files "fail loudly"; the code has no Blob backend and falls back to Postgres | `src/lib/storage.ts` |
| AGENTS.md says `BLOB_READ_WRITE_TOKEN` switches the backend; nothing reads it | `AGENTS.md`; `src/lib/storage.ts` |
| `attachment_bytes` exists only in SQL, not in `schema.ts` | `drizzle/0011_attachment_bytes.sql` |
