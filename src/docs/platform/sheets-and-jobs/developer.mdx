Scheduled work in MahekOne has no in-process scheduler. **The droplet's crontab** runs `deploy/sheet-sync.sh`, which calls **one HTTP endpoint**, `GET /api/sheets/sync?mode=…`, with a bearer `CRON_SECRET`. The route maps the mode to a **job name** and runs it through `runJob` in `src/lib/jobs.ts`. Every job writes a `job_runs` row; every sheet read additionally writes a `sheet_sync_runs` row and is guarded so only one run per source is in flight. The same jobs run from the Admin Console and from `npm run jobs -- <name>`.

## The endpoint

<Code file="src/app/api/sheets/sync/route.ts" symbol="JOBS" />

| Response | Meaning |
|---|---|
| 503 | `CRON_SECRET` is not set — the endpoint is closed |
| 401 | Wrong or missing bearer token |
| 400 | Unknown `mode`; the body lists the valid ones |
| 200 | `{ ok: true, job, recordsAffected, detail }` — for multi-step jobs, the **first** step's result |
| 409 | `SyncAlreadyRunningError` — another run of that source started less than ten minutes ago. Not a failure; callers log and move on |
| 500 | The job threw; `error` is the message |

`maxDuration` is 300 seconds; callers use `curl --max-time 310`. Query options pass through to `runJob`: `owner` (who projected rows are created as — required by `project`), `bills=1` (project bills from the Payment Status tab instead of Order Details), `leads=1`, `reassign=1`.

## One cycle

<Flow caption="sheet-sync.sh cycle (every :07 and :37 UTC)" chart={`
sequenceDiagram
  autonumber
  participant Cr as crontab
  participant Sh as sheet-sync.sh
  participant R as /api/sheets/sync
  participant J as runJob
  participant C as runSync
  participant G as Google Sheets
  participant DB as Postgres
  Cr->>Sh: cycle
  loop append, taken, payments, parties
    Sh->>R: GET ?mode=m (Bearer CRON_SECRET)
    R->>J: runJob(name)
    J->>C: runSync(source, mode)
    C->>DB: running row for this source in the last 10 min?
    alt yes
      C-->>R: SyncAlreadyRunningError - 409
    end
    C->>DB: insert sheet_sync_runs (running)
    C->>G: read windows past the watermark (5,000 rows)
    C->>DB: upsert staging rows whose hash changed
    C->>DB: run row - ok, counts
    R-->>Sh: 200
  end
  Sh->>R: ?mode=project with owner=SYNC_OWNER_EMAIL
  R->>J: project-sheet - customers, orders, bills
  Sh->>R: ?mode=field-activity, then field-activity-project
  Sh->>R: ?mode=punch-out-reminders
`} />

The order matters: the read modes land rows in staging and `project` publishes what has landed. One caller doing them in sequence guarantees that; five independent schedulers could not.

### `runSync`: one run per source

<Code file="src/lib/services/sheet-sync-core.ts" symbol="runSync" collapsed />

<Code file="src/lib/services/sheet-sync-core.ts" symbol="hashRow" />

A hash over the row's cells, **sorted by column name**, so inserting a column in the middle of a sheet does not rewrite thirty thousand hashes. An unchanged hash is not written, which is why a quiet tab costs a read and nothing else.

<DbEnum name="sheet_sync_mode" />

| Mode | Reads | Notices |
|---|---|---|
| `append` | From the watermark (highest row seen) onward | New rows |
| `reconcile` | The whole tab | Edits to old rows; rows gone from the sheet are **withdrawn** by difference, not by stamping |
| `reparse` | Nothing from Google — re-reads what is stored | A change in the **parsing rule**; run it whenever the reading of a row changes rather than the row |

### Decisions the sheet does not override

<DbTable name="sync_conflicts" note={{
  entity_type: "orders, customers …",
  field: "The column the sheet wanted to change, e.g. status or a manager seat.",
  sheet_value: "What the sheet says.",
  app_value: "What MahekOne holds, because a person decided it.",
  decided_by_id: "Who made the decision being protected.",
  resolved_at: "Null while open. A partial unique index keeps one open row per conflict, so an uncorrected sheet does not add a row every 30 minutes.",
}} />

- `orders.status` is kept wherever `approved_at` is set (accounts approved or declined it).
- The four manager seats on a customer are kept wherever `am_decided_at` is set (a deliberate reassignment); the party projection **and** the nightly `recomputeSalesPeople` both honour it.

<Callout kind="money" title="The sheet never writes money">
No path writes a receipt, `paid_amount`, a bill status or outstanding from a sheet. New bills are inserted with `payment_position = 'unstated'` (held out of outstanding, ageing, collections, slow-payer and reminders) and only on INSERT. A person's receipt or the receivables report states them. `revert-sheet-paid` exists to undo receipts an older importer wrote with `source = 'sheet_import'`, and touches nothing else.
</Callout>

## Cadence

| UTC | IST | Script mode | Endpoint modes |
|---|---|---|---|
| `:07`, `:37` | every 30 min | `cycle` | `append`, `taken`, `payments`, `parties`, `project&owner=…`, `field-activity`, `field-activity-project`, `punch-out-reminders` |
| `:22` | hourly | `hourly` | `hourly` |
| `20:13` | 01:43 | `nightly` | `reconcile`, `project&owner=…`, `field-activity-reconcile`, `field-activity-project`, `nightly` |
| `04:30` on the 1st | 10:00 on the 1st | `monthly` | `top-customers` |

`sheet-sync.sh` refuses to run if `DOMAIN`, `CRON_SECRET` or `SYNC_OWNER_EMAIL` is missing from `/opt/mahekone/.env`, and logs a `000` (no answer in 310 s) as "the server may still be running it" — the request reached the app and the job runs to completion server-side.

### By hand

```bash
npm run jobs -- nightly
npm run jobs -- project-sheet --owner=example@mahek.in --bills
npm run jobs -- taken-order-reparse             # the RULE changed, not the sheet
npm run jobs -- revert-sheet-paid --dry-run
npm run jobs -- customer-master-project --dry-run

ssh -N -L 5433:127.0.0.1:5432 deploy@one.mahekindia.com &
npm run jobs:prod:sheets -- customer-master-sync   # .env.local first, .env.prod.local second
```

Arguments are parsed by `src/lib/job-args.ts`: an unknown option, an `--owner` with no value, or a value given to a switch is **refused**, never silently dropped.

From the console, `triggerJob` lets a platform administrator run `nightly`, `hourly`, `day-boundary` and the one-offs; holders of `sheet.import` (the accounts desk) may run `sheet-reconcile`, `sheet-payments` and `project-sheet`.

## Changing it safely

<Steps>
<Step title="A new source is a staging table plus runSync">
Read with `readWindows`, hash with `hashRow`, write only changed rows, and wrap the work in `runSync` so the one-per-source rule and the run row come for free.
</Step>
<Step title="Never publish from the read step">
Reading lands rows; a separate projection publishes them. Keep the two as separate modes and order them in the caller.
</Step>
<Step title="A new mode is three edits">
The `JOBS` map in the route, a `case` in `runJob`, and the line in `sheet-sync.sh` (shipped automatically) — plus the crontab line on the droplet if it is a new cadence (not shipped).
</Step>
<Step title="When a parsing rule changes, ship a reparse">
Hash-driven syncs never revisit an unchanged row; without a reparse the new rule never lands.
</Step>
<Step title="Never let a projection write money">
No receipts, no `paid_amount`, no `status` or outstanding — and `payment_position = 'unstated'` on insert only.
</Step>
</Steps>
