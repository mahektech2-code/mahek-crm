Every outside service has **one client file** that owns the HTTP calls, reads its credential through `readSecret` (console first, environment second — see [Configuration](/docs/platform/configuration/developer)), and returns a result type rather than throwing. Each also has a **readiness** question the screens ask before drawing the feature. No SDKs are used where a `fetch` will do: Google, Wati, MiniMoth, Resend, Ola and S3 are all plain HTTP; only dictation's OpenAI path goes through the AI SDK.

## Wati

### Sending

`src/lib/wati.ts` talks to Wati's v3 API with a Bearer token and **decides nothing** — whether a message may go (the founder's switch, an approved template, the number, the weekly limit <Setting k="whatsapp.contactsPerWeekLimit" />) is `whatsapp-service.ts`'s question, asked before the client is called.

<Code file="src/lib/wati.ts" symbol="watiConfig" />

The founder's switch is the newest row of `whatsapp_service_events` (no row means off), read on every send rather than cached. `whatsapp.activate` is the capability that flips it.

## MiniMoth and sign-in codes

<Code file="src/lib/services/otp-service.ts" symbol="otpAvailability" collapsed />

| Order | Provider | Condition |
|---|---|---|
| 1 | MiniMoth | `minimoth.apiKey` held, and not an `mm_test_` key while `NODE_ENV=production` |
| 2 | Wati authentication template | <Setting k="auth.otp.whatsappTemplateName" /> named, a Wati key held, and the template approved in Wati |
| — | None | `available: false` with a reason; the login page shows passwords only |

MiniMoth generates and verifies the code (`sendMiniMothOtp`, `verifyMiniMothOtp`); MahekOne's `auth_otps` row records that one was sent and the MiniMoth id. The destination is the HRMS personal mobile of the linked employee. Limits are settings: <Setting k="auth.otp.ttlMinutes" />, <Setting k="auth.otp.maxVerifyAttempts" />, <Setting k="auth.otp.resendCooldownSeconds" />.

<Callout kind="warn">
`otpAvailability` never throws — the container's health check is the login page, so a settings read failing during a migration must cost the code option, never the sign-in screen.
</Callout>

## Ola Maps

Five named credentials rather than one list, spent in order. With one key held, calls go straight through; with several, a quota refusal is recorded and the next key is used, and the spent one is skipped for <Setting k="maps.olaKeyCooldownHours" /> hours.

<Code file="src/lib/services/ola-key-service.ts" symbol="olaGet" collapsed />

| Use | Where | Key travels to |
|---|---|---|
| Live and Territory maps (tiles, style, glyphs) | `src/app/sales/live/page.tsx`, `src/app/sales/territory/page.tsx` → `ola-maps.tsx` | The **browser**, as a prop from `liveOlaKey()` — restrict it to the domain in Ola's console |
| Handset map | Sync payload to a bound device | The **phone** — use a separate key with a spend cap; Ola offers no package restriction |
| Snap-to-Road | `road-snap-service.ts`, asked once per selected salesman per day by `/api/sales/live/snap-trail` | Server only |
| Geocoding, places, directions, distance | `ola-geocode-service.ts` and siblings, `geocode-customers` job | Server only |

The key is never put in the style URL on the handset — requests are signed at the HTTP layer so offline map packs are stored key-less and survive a key rotation.

## Google service account

<Code file="src/lib/sheets.ts" symbol="sheetsConfigured" />

A self-signed JWT (RS256, `spreadsheets.readonly` scope) is exchanged for an hour-long token, cached in module scope with a minute of headroom. `GOOGLE_SA_PRIVATE_KEY` is stored with literal `\n`; the client converts them, and "invalid JWT signature" from Google almost always means that conversion did not happen. The service account must hold **Viewer** on each workbook.

## Expo push

<Code file="src/lib/mbos/push.ts" symbol="pushReadiness" collapsed />

Tokens are registered by the handset at `POST /api/mbos/push-token` onto `mbos_devices.push_token`. Sends go to `https://exp.host/--/api/v2/push/send` in chunks of 100; `collectPushReceipts` reads receipts hourly and clears tokens Expo reports as `DeviceNotRegistered`. See [Handset release](/docs/platform/handset-release/developer#push-notifications) for the Firebase setup.

## The public website

`/api/public/enquiries` compares the presented secret with `readSecret("enquiries.ingestSecret")` in constant time and refuses anything else; duplicates are reported rather than created twice. It is server-to-server only — the secret never reaches a browser on either side.

## Adding an integration

<Steps>
<Step title="Declare the credential">
Add a name to `SECRET_NAMES` with its environment fallback, and to `.env.production.example` (commented) so `env-names.test.ts` agrees.
</Step>
<Step title="One client file">
Plain `fetch` with a timeout, `readSecret` per call (no caching of keys), a result type rather than a throw.
</Step>
<Step title="A readiness function the screen asks first">
Missing key → the feature is not drawn, or says it is not set up. Never draw a control that fails when pressed.
</Step>
<Step title="Inbound webhooks authenticate before parsing">
A derived path token or a shared secret, compared in constant time; cap the body size; answer 404 to a wrong token.
</Step>
<Step title="A row on the Integrations screen">
Via `secret-credential-row.tsx`, so a deploy nobody has shell access to can still be connected.
</Step>
</Steps>
