MahekOne is one Next.js 16 application talking to one Postgres database, plus a separate Expo project for the field salesman's handset in `mbos-app/`. Getting a laptop from a fresh clone to a running app takes four commands, and **only one environment variable is required** — `DATABASE_URL`. Everything else (Google Sheets, WhatsApp, dictation, mail, file storage) is optional locally and switches itself off, saying so on the screen, when its variables are missing.

This page is the whole path: what to install, what `npm run db:setup` actually does, how migrations are written in this repository (by hand — never generated), the test suites, the handset, and the failures that look like success.

## What `npm run db:setup` does

`db:setup` is `node scripts/setup-db.mjs`. It has five numbered stages and prints each as it goes:

| Stage | What happens | When it stops |
|---|---|---|
| **1. Environment** | Copies `.env.example` to `.env.local` if `.env.local` does not exist; otherwise leaves it alone. Reads `DATABASE_URL` out of it. | No `DATABASE_URL` → stops with "No DATABASE_URL in .env.local". A URL that is **not** `localhost`/`127.0.0.1` → warns that seeding a shared database would wipe it, and exits without touching anything. |
| **2. Postgres** | Finds `psql` on `PATH`, or under Homebrew's `/opt/homebrew` or `/usr/local` for `postgresql@17` down to `@14`. Runs `select 1` against the `postgres` database. | Not installed → prints the `brew`/`apt` or `docker run` command for your platform. Installed but not listening on 5432 → prints how to start it. |
| **3. Role and database** | Creates the `mahek` role (login, `createdb`) and the `mahekone` database owned by it, each only if missing. | No permission → suggests running the `create role` as a superuser. |
| **4. Schema** | `npx drizzle-kit migrate` — every migration in `drizzle/`. | Whatever drizzle-kit does (see [Troubleshooting](#troubleshooting): it can exit having applied nothing). |
| **5. Demo data** | `npm run db:seed`. | — |

It ends with "Ready. Start the app with: npm run dev".

<Callout kind="warn" title="Re-running it reseeds">
Stage 5 runs every time, and the seed **wipes and reseeds** the book (it also clears sessions). If you only want to catch up on migrations, run `npm run db:migrate` instead.
</Callout>

## Migrations

The schema is declared in `src/db/schema.ts` (Drizzle ORM) and changed by SQL files in `drizzle/`, listed in order in `drizzle/meta/_journal.json`. `drizzle.config.ts` points drizzle-kit at both.

| Command | What it runs | Use it for |
|---|---|---|
| `npm run db:migrate` | `drizzle-kit migrate` | Catching your local database up |
| `npm run db:deploy` | `node scripts/migrate-deploy.mjs` | The deploy (and CI's `stack` job). Same migrator, but it prints the real Postgres error and counts what was applied |
| `npm run deploy:db` | `db:deploy && catalogue:deploy && hire:deploy` | What `deploy.yml` runs over the SSH tunnel: migrations, the idempotent catalogue import, and Hire's install step |
| `npm run db:generate` | `drizzle-kit generate` | **Do not use** — see below |

### Write migrations by hand

<Rule title="Never run drizzle-kit generate in this repository">
`drizzle/meta/` holds snapshots for only a few dozen of the more than two hundred migrations, so `generate` diffs against a schema hundreds of migrations out of date and emits a "new" migration that re-creates tables that already exist. It also stamps `when` from the wall clock, which can land below the hand-written values. Write the `.sql` file yourself, append the journal entry yourself, and never commit a generated `meta/NNNN_snapshot.json`.
</Rule>

The house style is a prose comment at the top saying what the migration is for and any trap it avoids. The most recent one is a good model:

```sql
-- Documentation: its own MahekOne app, at /docs.
--
-- The app id is added here and USED nowhere in this file: a value added to an
-- enum cannot be used in the transaction that adds it, and drizzle-kit runs
-- every pending migration in one. Granting it is `npm run app:grant -- docs`
-- or the Access screen, after this has committed.
alter type "public"."app_id" add value if not exists 'docs';
```

Statements within one file are separated by `--> statement-breakpoint`.

### The journal and `when`

Each journal entry has an `idx`, a `tag` (the file name without `.sql`) and a `when`. **drizzle decides what is pending by comparing each entry's `when` with the newest `created_at` in `drizzle.__drizzle_migrations`** — it does not check that every entry was applied. Three things follow:

- A new entry's `when` must be **above every existing one**. Take the last entry's value and add a small step; recent entries step by 1000.
- A migration written on a branch while `main` moved on may carry a `when` below `main`'s newest. Once both land, it is **skipped for ever** and the run still reports success. When `_journal.json` conflicts in a merge, `main`'s entries are authoritative: renumber your files above `main`'s highest index and make the `when` sequence strictly increasing across the whole file.
- File numbers and `idx` can diverge (there are gaps in the `NNNN_` prefixes). The journal, not the file name, is the order.

`migrate-deploy.mjs` exists to make these visible. It counts `drizzle.__drizzle_migrations` before and after, prints "N applied, now X of Y in the journal", and emits a `::warning::` naming the watermark trap when fewer rows exist than journal entries. On failure it prints the driver error's `code`, `detail`, table, column and constraint (drizzle-kit's own CLI prints nothing), and for an "already exists" error it queries what is actually there:

<Code file="scripts/migrate-deploy.mjs" symbol="appliedCount" />

### Enum values: add in one, use in a later commit

<Rule title="A value added to an existing enum cannot be used in the same run">
`drizzle-kit migrate` applies **every pending migration in one transaction**, and Postgres refuses to use a value added by `ALTER TYPE … ADD VALUE` until that transaction commits. So no later migration in the same batch may reference it either — not in an `INSERT`, a `CHECK`, or an index predicate. It passes on every developer's database (which already committed the value long ago) and fails only from scratch: CI and a fresh clone.
</Rule>

- Compare as text instead: `o.status::text in ('captured', …)` needs no enum member.
- Grants of a new `app_id` go through `npm run app:grant`, never a migration.
- Renaming an app slug is `ALTER TYPE app_id RENAME VALUE`, never add-and-migrate.
- A brand-new type created with `CREATE TYPE … AS ENUM` and used in the same file is fine — the restriction is only on values added to an already committed enum.

### Every migration must be additive

The deploy migrates **before** the new image starts, while the old code is still serving (see [Deploying](/docs/platform/deploy-digitalocean#a-deploy-step-by-step)). New columns, new tables and backfills that match on `updated_by_id is null` are safe. Dropping or renaming a column the running code reads needs two releases: one that stops reading it, then one that removes it.

### Checking a migration before you push

1. Apply it to a database built from nothing — `npm run test:db` rebuilds `mahekone_test` from every migration, which is exactly the from-scratch case. (It drops and recreates `mahekone_test`; if somebody else is running integration tests against the same Postgres, use a throwaway database instead.)
2. Query `information_schema.columns` for a column your migration adds. "Applied successfully" is not evidence.
3. CI's `ci` job runs `db:migrate` against an empty database, and the `stack` job runs `deploy:db` the way the deploy does.

## Seed data

```bash
npm run db:seed        # tsx src/db/seed.ts
```

The seed **wipes and reseeds** a deterministic demo book (a fixed pseudo-random seed, so a reseed produces the same customers), imports the product catalogue, creates the demo accounts with their app grants, and then runs the engines over the seeded book so the derived caches are filled. It also clears every session, so you will be signed out.

Every seeded account has the same password, given in `AGENTS.md`, and signs in with its email or its work number. The full list is in `AGENTS.md` under **Seeded accounts**. By role:

| Seeded account | App and level | Lands on |
|---|---|---|
| Four telecaller accounts | CRM, associate | Straight into the CRM |
| A CRM associate with Reports | CRM and Reports, associate | The launcher |
| The manager account | CRM manager, Accounts, HRMS admin, Admin Console, Founder | The launcher |
| The field salesman account | `field` (the handset) only | `/apps`, which says there is nothing for him in a browser |
| The ledger-desk account | Accounts, manager | Straight into order approvals |

`npm run demo:clear` removes the demo data again.

### Granting apps the seed does not give

New apps (Documentation, ERP, Hire and others added after the seed was written) are not granted by it. Grant one by hand:

```bash
npm run app:grant -- docs example@mahek.in               # associate
npm run app:grant -- hrms example@mahek.in --level=manager
```

`scripts/grant-app.ts` takes an app id and an email or work number, always writes a level (associate unless `--level` says otherwise), re-derives the account's own level from all its grants, and is idempotent. `admin` granted at `--level=admin` is what makes a platform administrator. Related helpers: `npm run user:password`, `npm run user:role`.

### The documentation index

The docs pages quote code with `<Code file symbol>`, and production runs Next's standalone server with no source tree beside it. So `scripts/docs-index.mjs` cuts every quoted excerpt out of the source at build time, highlights it, and writes it with the page headings and search text to `src/docs/_generated/index.json`.

```bash
npm run docs:index              # write it
node scripts/docs-index.mjs --check   # exit 1 if the committed file is stale
```

It exits non-zero naming any `<Code>` whose file or symbol does not exist. A symbol must be a top-level `function`, `const`, `let`, `type`, `interface`, `class` or `enum` declaration. Because `prebuild` runs it, a page quoting a renamed function fails `npm run build`, not a reader.

### How the integration runner finds its database

Every runner reads `DATABASE_URL` from `.env.local` and **replaces the database name with `mahekone_test`**, sets `NODE_ENV=test`, and runs `tsx --conditions=react-server --test <file>`. So your development database is never touched. Individual suites also assert the URL matches `mahekone_test` in their `before` hook ("Integration tests must run against mahekone_test. Run `npm run test:db` first."), and each suite truncates the tables it uses itself.

Files run sequentially because they share one database and truncate the same tables: run in parallel they produced unique-key violations and a different failure count on every run. The runner keeps going after a failure and prints "N of M integration suites failed". `src/lib/mbos-columns.test.ts` runs first — a schema column that no migration created breaks every other suite with "column does not exist", and that one test says which table.

## Troubleshooting

### `tsc` is quiet, exits 0, and checks nothing

`tsconfig.json` includes `.next/dev/types/**/*.ts`. When that generated file is stale it can contain a syntax error; `tsc` then reports only those parse errors, **exits 0, and never checks `src/`**. If `npx tsc --noEmit` looks suspiciously clean, or its only output names `.next/dev/types/routes.d.ts`:

```bash
rm -rf .next/dev tsconfig.tsbuildinfo
npx tsc --noEmit
```

Plant a deliberate type error in a `src/` file now and then to prove it is really checking.

### `db:migrate` says "applying migrations…" and applies nothing

Two different causes look identical:

1. **The watermark.** A row in `drizzle.__drizzle_migrations` carries a `created_at` above some journal entries (often from a branch you once ran). Every entry below it is skipped, silently, for ever.
2. **An enum value used in the same batch.** drizzle-kit exits 1 with no error text. Run `npm run db:deploy` instead — it prints the real Postgres error.

Either way, compare what is applied with the journal:

```sql
select count(*) from drizzle.__drizzle_migrations;
select created_at from drizzle.__drizzle_migrations order by created_at desc limit 5;
```

against the number of entries and the `when` values in `drizzle/meta/_journal.json`. To catch up **without** wiping your data, apply each missing `drizzle/<tag>.sql` yourself — split on `--> statement-breakpoint`, run the statements in one transaction — then insert its `sha256` hash with the journal's `when` as `created_at` into `drizzle.__drizzle_migrations`. Or, if the data does not matter, `npm run db:setup` against a freshly dropped database. Before blaming `main`, build a database from `main` alone.

### Every page returns 200 but is broken

A database missing recent migrations does not fail visibly. Next renders the error boundary inside the shell and still answers **200** with a full-size body, so a `curl -w "%{http_code}"` smoke test over every route is all green while every page is broken. Check the migration count first, then assert on content (a string only the real screen renders) and grep the dev-server log for `PostgresError`.

### `TurbopackInternalError: Symlink … node_modules is invalid`

Building a copy of the repository outside the working tree with a symlinked `node_modules` fails: Turbopack refuses a symlink pointing out of the project root. Hard-link the tree instead:

```bash
rsync -a --link-dest="$REPO/node_modules/" "$REPO/node_modules/" ./node_modules/
```

### Other traps worth knowing

| Symptom | Cause |
|---|---|
| Integration failures vary between runs | Two sessions sharing one `mahekone_test`, or `test:db` run while another session's tests are running. Use your own copy of the database. |
| "Cannot find module 'server-only'" across many suites | `node_modules` was deleted or reinstalled mid-run. Infrastructure, not your change. |
| A `timeout … tsc` pipeline reports nothing on macOS | macOS has no `timeout` binary, so nothing ran. Print exit codes. |
| A raw `db.execute` returns a string where the type says `Date` | Raw SQL returns timestamps as strings; use `asDate()`. |
| A `sql` template with prose comments fails strangely | A backtick inside a `` sql`…` `` literal ends it. `sql-backticks.test.ts` guards this. |
