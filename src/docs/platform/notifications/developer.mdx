A notification's app is **derived from its link**, never stored. `notificationAppOf` (pure, client-safe) and `notificationAppSql` (server) are two readings of one rule, both built from `APP_ROUTES` — the prefix list `proxy.ts` uses to name a request's app — and `notification-apps.db.test.ts` runs both over the same links and fails if they ever disagree.

## Rules the code keeps

- **Writers do nothing new.** Every `insert(notifications)` and `notifyUsers` call already names a link; that link decides the app. A new kind of notification needs no app field — give it the right `href`.
- `href` decides first; a row with no `href` and an `mbos_href` is `field`; anything else is general (`null`) and shows in every bell.
- A prefix matches a whole path segment (`/crm` and `/crm/…`, `?…`, `#…`; never `/crmx`).
- `notificationAppSql` refuses a route whose prefix or app id is not plain lower-case letters, slashes and hyphens, because it is spliced into SQL.
- An answer that arrives after the tab moved to another app is dropped (`asked !== appRef.current`), so the ERP header never paints the CRM's list.

## The pop-up

`popsUpIn(app)` is true for every app except `field`, which never reaches a browser; the centre itself keeps the pop-up off `/factory`, `/login` and `/erp/print`. `nextPopups` keeps the stack: who was waiting, then what came due, then what arrived.

Remind me sends a code from `SNOOZE_CHOICES` (`15m`, `30m`, `1h`, `3h`, `tomorrow`), never a number of minutes. `answerNotifications` rejects any other code and works out the instant with `remindAtFor` on the server's clock; `tomorrow` is 10:00 IST the next day. It only touches your own unread rows.

**Shown means due.** When a notification first enters the stack, the centre calls `answerNotifications(ids, "shown")`, which sets `remind_at = now()` where it is still null. `notificationFeed` returns unread rows with `remind_at <= now()` as `due`, so a shown-but-unanswered notification comes back after a reload, in another tab or on another machine until it is done or snoozed. Older unread rows that were never shown have no `remind_at` and do not flood the screen. There is no scheduled job: the polling brings reminders back.

Take action now marks that one read, goes to its link, and holds the rest (`HOLD_ON_ACTION_MS`, ten minutes) until the path leaves the page it opened. Nothing about the rest is written; they are still due. The pop-up does not open over another dialog or while the cursor is in a field.

## Where a notification goes

`notifyUsers` refuses, at compile time, an entry that names no destination. It takes `href`, `mbosHref`, or an explicit `general: true`. `reachesHandset(href, mbosHref)` decides the handset list and the push from the same two links: a handset link, or no link at all. `/notifications` is the handset link when no screen is more precise. A raw insert into `notifications` is held to the same rule by a test in `notification-apps.test.ts`, and it does not push.

`mbos_devices.notification_permission` is what each phone answered, shown beside whether it holds a token on Admin Console → Handsets. A phone can allow notifications and still hold no token: see "Push notifications" in `DEPLOY.md`.
