Configuration in MahekOne is three stores with three different rules: **settings** (`app_settings`, declared in one registry, cached, audited with values), **credentials** (`app_secrets`, read only by the request about to spend them, audited without values), and the **process environment** (read at start-up or per request from `process.env`). This page covers the code behind each, how to add a setting without breaking the server build, and every environment variable the code actually reads.

## Map of the code

| Layer | File | What lives there |

### Who may write which key

`requireConfigWriteFor(keys)` in `src/lib/actions/crm.ts` asks for `config.write` and then, for anybody who is not the platform administrator, that **every** key's page (via `placeSetting`) is owned by an app they hold at manager or admin level. Platform-page keys and keys marked `adminOnly` in `PRESENTATION` are the platform administrator's alone, and the platform administrator must have confirmed their password within <Setting k="auth.console.confirmMinutes" />.

<CapabilityGrid names={["config.write"]} />

### Settings on the handset

`mbos.*` keys reach the handset on every pull as part of the configuration channel, so a change made at a desk lands on phones on their next sync. The handset reads them from its local cache; a key that is not sent falls back silently to the handset's default, which is why `mbos-wire.test.ts` pins the spelling of the keys both sides share.

## Adding a setting

<Steps>
<Step title="Add the registry entry">
In `SETTINGS` in `src/lib/config/registry.ts`: key, type, category, label, a description a manager can act on, a default, and `min`/`max` or `options`. Never type the number into an engine.
</Step>
<Step title="Add the Config type entry — or the server build breaks">
`Config` is a **hand-written** type further down the same file. A key in `SETTINGS` with no entry in `Config` type-checks in most places and fails `next build` where `getConfig()["your.key"]` is read.
</Step>
<Step title="Place it on a page">
Make sure a rule in `settings-placement.ts` (or a tab in `PRESENTATION`) places it. `settings-placement.test.ts` fails the build on a setting that sits on no page — a setting nobody can find cannot be changed.
</Step>
<Step title="Add a consistency rule if it pairs with another key">
In `checkConsistency`, with a sentence that names both keys.
</Step>
<Step title="Read it through the engine's config type">
Pass it into the pure engine as an argument; read `getConfig()` in the service.
</Step>
<Step title="Changing a shipped default">
Write a migration that updates the stored value **only where `updated_by_id is null`**, so a value somebody chose is left alone (see `0042_day_boundary_midnight`, `0120_check_in_is_a_gate`).
</Step>
</Steps>

<Callout kind="warn">
A setting whose default is `null` breaks every integration test unless it is marked `nullable` and written through `storedSettingValue` — `app_settings.value` is `jsonb NOT NULL`.
</Callout>

### Reading one

`readSecret` is the only function that selects a value. The console row wins; the environment is the fallback. It is deliberately **not cached**, so a rotated key stops working at once.

Screens call `secretStatuses()`, which selects `last4` and the source (`console`, `environment` or `unset`) and never the value:

<DbTable name="app_secrets" note={{
  name: "A SECRET_NAMES key, e.g. wati.apiToken.",
  value: "The key as typed. Not encrypted — there is nowhere to hold an encryption key the app can read and a dump cannot.",
  last4: "The tail, for telling keys apart on a screen.",

Writes go through `setSecretAction` / `clearSecretAction` (platform administrator only), which audit `secret.set` / `secret.clear` with the name and never the value.

<Callout kind="note" title="The one exception: the Ola Maps key">
A map tile key must reach whoever draws tiles, so the Ola key is handed to the browser as a prop by the page that draws the map, and to a bound handset in its sync payload. The mitigations are a domain restriction in Ola's console for the web key and a **separate** key with a spend cap for the handset. See [Integrations](/docs/platform/integrations/developer).
</Callout>

## `.env.local` and `.env.prod.local`

- **`.env.local`** is the laptop's own environment: `DATABASE_URL` to your local Postgres, and whatever optional keys you are testing. `npm run jobs`, `db:seed` and the other `tsx` scripts pass `--env-file=.env.local`.
- **`.env.prod.local`** holds a `DATABASE_URL` pointing at production **through an SSH tunnel** (`ssh -N -L 5433:127.0.0.1:5432 deploy@one.mahekindia.com`). `npm run jobs:prod` loads only that file.
- **`npm run jobs:prod:sheets`** loads `.env.local` **first** (for the Google credentials) and `.env.prod.local` **second**, so production's `DATABASE_URL` wins.

<Callout kind="warn" title="The order of the two files is the whole safety">
With the files reversed, `.env.local`'s `DATABASE_URL` wins, and a "production" job writes to your local database and reports success. A prod job also runs **your checkout's** code, not what is deployed — make sure your tree is current with `main` first.
</Callout>

## Known gaps

| Gap | Where |
|---|---|
| `msg91.authKey` is a settable credential that no code reads | `src/lib/secrets.ts` `SECRET_NAMES` |
| `attachments.retentionDays` is on the Settings screen but never read | `src/lib/config/registry.ts`; `src/lib/services/attachment-service.ts` |
| `workingDay.timezone` is a setting but SQL uses the `APP_TIMEZONE` constant | `src/lib/business-date.ts` |
| `getConfig` caches per process; there is no cross-process invalidation | `src/lib/config/store.ts` |
| `Config` is hand-typed beside `SETTINGS`; nothing derives one from the other, so a missing entry fails only `next build` | `src/lib/config/registry.ts` |
| `app_secrets.value` is stored in clear; a leaked unencrypted dump leaks every console-set key | `src/db/schema.ts` `appSecrets` |
