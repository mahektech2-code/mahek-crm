The Sales Dashboard is the App Router tree under `src/app/sales/`, one layout that gates the `sales` grant and draws `SalesShell`, and a large read service — `src/lib/services/sales-service.ts` — whose every query narrows itself through `managerScope()`. Writes are server actions in `src/lib/actions/sales.ts` (plus `sales-targets.ts`, `field-activity.ts` and the lead actions), each opened by `requireSalesAccess`. The handset writes through a different door entirely: `src/lib/actions/mbos.ts`, authenticated by a device token.

### The layout gate

The layout checks the **grant** and that at least one module is held, then hands the shell an `allowed` list of hrefs so the sidebar draws only what the person may open. Each module folder repeats the check for its own key, so a bookmark past a withheld module redirects.

`modules.test.ts` compares `SALES_NAV` with the registry, so a module declared and never drawn fails the build — four screens once drifted out of the sidebar unnoticed.

## Scope: `managerScope`

Resolved **inside the service, from the session**, never passed in: a filter a caller can forget to pass is a filter that leaks.

`onlyMine` turns the scope into a clause. `null` means national and renders nothing; an empty list renders an `in ('')` that matches nothing.

<Callout kind="warn" title="managerScope guards photographs too">
`canReadAttendanceSelfie` and `canReadTravelLegPhoto` narrow through `managerScope`. Never widen it for a coverage screen — use `placeScope` / `mineByPlace`, which widen three WHERE clauses on Territory and nothing else. Both photo checks also ask for the `sales` grant first, because the scope is national for anybody with no region rows.
</Callout>

## Writes: `requireSalesAccess`

A write that lands on a person then asks `salesmanOutsideScope(id)`, which reads `scopeCovers` against the same `managerScope` the screen drew from. Every decision tells the person through `tell`, which writes a notification row and a push with an MBOS deep link (`mbosHref`), never a MahekOne route the salesman cannot open.

The Sales Dashboard mostly gates on **level + module**, not on capabilities. `target.set` (Sales Targets), `order.approve` (accounts' order queue) and the two lead approvals are the exceptions.

## Adding a Sales Dashboard screen safely

<Steps>
<Step title="Declare the module">
Add a `sales(...)` entry to `lib/modules.ts`, then the same href to `SALES_NAV` in `nav.ts` with an icon — or to `NOT_IN_SIDEBAR` with a reason.
</Step>
<Step title="Guard the folder">
Give it a `layout.tsx` calling `requireModule(user.id, "sales.<key>")`.
</Step>
<Step title="Read through managerScope">
Put the query in a service and narrow it with `onlyMine(await managerScope(), column)`. Never accept a scope argument from the page.
</Step>
<Step title="Gate every write">
Open the action with `requireSalesAccess(SALES_MANAGER("sales.<key>"))` and check `salesmanOutsideScope` for every person it touches. Tell the person with `tell(...)` and a handset href.
</Step>
</Steps>
