Orders, receipts and bills are the CRM's own tables — `orders`, `payment_receipts`, `bills` — with `source = 'mbos'` marking what came from a handset. The handset writes them through the sync dispatcher in `src/lib/actions/mbos.ts`; the three Sales Dashboard screens are read-only views over them in `src/lib/services/sales-service.ts`, narrowed by `managerScope`. Approval and confirmation happen in the Accounts app.

Things a change must preserve:

- **The same id from the same salesman is a resend**, accepted with the stored number. The same id from someone else is a `duplicate` rejection.
- **The delivery party is not scope-checked** — it is an address on someone else's order and routinely in another book.
- **The credit check reads outstanding now.** `outstanding_stale` is chosen over `credit_exceeded` when the handset's figure moved and was older than `mbos.credit.outstandingStaleHours`.
- **Never bind a `Date` into raw SQL** here — pass `.toISOString()`. This handler once refused every order because of it.

### Scope

<Code file="src/lib/services/sales-service.ts" symbol="onlyMine" />

`managerScope` resolves the session itself — no call site can forget to pass it. `salesmanIds: null` means national; an associate gets `[self]`. Orders narrow on `o.created_by_id`, receipts on `r.reported_by_id`, invoices on `coalesce(c.sales_am_id, c.owner_id)` restricted to holders of the `field` app.

## Changing it safely

<Steps>
<Step title="Re-check on the server anything the handset decides">
A sync endpoint accepts payloads from a device somebody owns. A rule only in the APK is not a rule.
</Step>
<Step title="Count in SQL, page in SQL">
Every figure above a table is an aggregate over the scoped book. Never derive a figure from the capped page.
</Step>
<Step title="Keep money paths keyed on confirmed">
Nothing here may reduce a bill. A reported receipt changes no balance.
</Step>
<Step title="Add a new rejection code with words">
The salesman reads the message on his Not accepted list; it must name the customer and the way forward.
</Step>
</Steps>

## Known gaps

| Gap | Where |
|---|---|
| `mbos.orders.approvalThresholdPaise` / `secondTierThresholdPaise` describe a manager sign-off the server never applies; only the handset credit engine reads the first | `registry.ts`; `mbos-app/src/engines/credit.ts` |
| `mbos.credit.overdueDaysBlockOrders` is not re-checked by `handleOrder` | `actions/mbos.ts` `handleOrder` |
| Deposit window shown as "working day(s)" but computed as `hours / 24` against calendar days (`current_date - received_at`) | `payments/page.tsx`; `sales-service.ts` `RECEIPT_COLUMNS` |
| Invoices narrow on `coalesce(sales_am_id, owner_id)`, not `ASSIGNED_TO_SQL` | `sales-service.ts` `fieldInvoiceWhere` |
| AGENTS.md: "`handleOrder` refuses one against a lead below negotiation" — the code converts the lead instead | `actions/mbos.ts` `handleOrder` |
| A bounced cheque changes no status; reversal is left to accounts by notification | `actions/mbos.ts` `handlePaymentUpdate` |
